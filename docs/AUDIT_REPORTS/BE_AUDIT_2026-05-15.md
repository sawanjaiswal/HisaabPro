# HisaabPro Backend Audit — 2026-05-15

## Methodology

Systematic review of backend layers for all major features (parties, invoicing,
payments, products, stock, loans, expenses, GST, etc.). Inspected DB schema
(Prisma) for indexes and NOT NULL constraints, route handlers for
auth/validation/idempotency, service layer for tenant scoping and transaction
usage, and offline contract compliance per `OFFLINE_RULES.md`. Examined ~599
route handlers, 42 schema files, and critical service paths covering money
handling, error responses, and logging.

## P0 Findings (Ship-Blocker)

None. No auth bypass, tenant leak, money-as-float, missing migration on shipped
feature, or secrets in logs detected.

## P1 Findings (Must-Fix Before Next Release)

### 1. Missing idempotency key on party creation route

**File:** `server/src/routes/party.ts:44–53`

```ts
router.post(
  '/',
  requirePermission('parties.create'),
  validate(createPartySchema),
  asyncHandler(async (req, res) => {
    const businessId = req.user!.businessId
    const party = await partyService.createParty(businessId, req.body)
    sendSuccess(res, { party }, 201)
  })
)
```

**Issue:** Critical mutation lacks `idempotencyCheck()` middleware. If offline
sync retries a party creation due to network flakiness, it will create
duplicates. Documents (`/documents CRUD`) correctly use idempotency
(party.ts:62 reference); parties should too.

**Impact:** Data integrity risk — duplicate parties break ledger aggregation
and affect outstanding-balance calculations.

**Fix:**
```ts
router.post(
  '/',
  requirePermission('parties.create'),
  replayProtection,
  idempotencyCheck(),
  validate(createPartySchema),
  asyncHandler(...)
)
```

## P2 Findings (Tech Debt / Cleanup)

### 1. Loan service uses `include: { transactions: {…} }` instead of `select`

**File:** `server/src/services/loan.service.ts:58–61`

```ts
const loan = await prisma.loanAccount.findFirst({
  where: { id: loanId, businessId },
  include: {
    transactions: { orderBy: { date: 'asc' } },
  },
})
```

While not a leak (loanAccount is business-scoped), `include: true` fetches all
fields. Explicit `select` is cleaner and prevents accidental over-fetch if the
schema later adds new relations.

**Fix:** Use `select` with explicit field lists for transactions.

### 2. `createdBy` field nullable in Document/Expense for legacy rows

**File:** `server/prisma/schema.prisma:1963`

```
createdBy String? // userId; nullable for pre-existing rows
```

Intentional for data migration. No action — flagged for awareness so future
NOT-NULL migration sees the context.

## Cross-Cutting Observations

1. **Tenant scoping is consistently applied.** Every `findMany`/`findFirst` in
   service layer includes `businessId` in the where clause. Composite indexes
   on `[businessId, partyId]` etc. are comprehensive. No tenant-leak risks
   identified.

2. **Transaction usage is correct.** Payment creation, document
   creation/update, and loan transactions all wrap multi-step writes in
   `prisma.$transaction()`. Stock deductions batch correctly.

3. **Error handling is centralized.** Custom `AppError` class with factories
   (`notFoundError()`, `insufficientStockError()`). Sensitive fields (tokens,
   passwords, OTPs) redacted in logs by `errorHandler.ts`. Status codes
   (401/403/404/409) semantically correct.

4. **Auth + authorization enforced.**
   - All protected routes use `auth` middleware.
   - `requirePermission()` on mutations.
   - Public routes explicitly scoped to `/api/p/`.
   - Rate limiting tiered: `authRateLimiter` (5 req/min for login/OTP),
     `userMutationLimiter`, custom limiters for ledger queries (30 req/min).

5. **Money is always integer paise.** No `parseFloat()` on money fields.
   Product pricing, credit limits, payment amounts all `Int`. The few
   `Decimal(12,2)` fields are referral wallets — intentional, not transaction
   money.

6. **Offline contract is partially enforced.**
   - Critical mutations (documents, payments, expenses) use `idempotencyCheck()`.
   - `entityType` + `entityLabel` passed for queue UI.
   - FE `scripts/enforce-offline.mjs` prevents raw `fetch()` outside allowlist.
   - **Gap:** party creation (and a few non-document mutations) lack
     idempotency keys — tolerable today, risky as offline sync expands.

## Recommendations

1. **Immediate (before ship):** Add `idempotencyCheck()` to party creation
   route (P1).
2. **Next sprint:** Audit which other non-document POST routes (FY closure,
   referral, expense-budget, custom-fields, batches) should be idempotent if
   offline sync may replay them.
3. **Tech debt:** Replace `include: true` with explicit `select` in
   `loan.service.ts` and similar patterns. Scan for any remaining uses of
   `include` without field limits.
4. **Monitoring:** Watch logs for email addresses in errors — consider a PII
   filter middleware that hashes the local-part in production before storage.
